# TH04 MAIN shared random-ring semantics (v1244)

## Scope

This batch documents the state and access contract implemented by:

- `src/main/math/randring_state.asm`
- `src/main/math/randring_fill.cpp`
- both `randring1_*` and `randring2_*` accessor families
- the half-open range helpers in `randring.hpp` and `randring_ranges.hpp`

The edit adds source comments and renames one local loop index. It does not
change a public symbol, translation-unit boundary, segment, calling convention,
instruction order, global layout, or accepted unit extent.

## One shared stream

`randring_state.asm` declares exactly one 256-byte `_randring` followed by one
word `_randring_p`. The `1` and `2` suffixes distinguish accessor copies placed
in different MAIN code groups. They are not separate random streams: every
accessor loads and mutates the same `_randring_p`, so player, background,
enemy, boss, item, and bullet calls can affect each other's later samples.

`stage_runtime_init()` calls `randring_fill()` once while resetting a stage
session. The fill performs 256 far Pascal `IRand()` calls in descending index
order, from 255 through 0, and then clears the complete word cursor. Reversing
that fill direction would change which generated byte occupies each index even
though the number of `IRand()` calls stayed the same.

## Overlapping word samples

All six accessors share this ordering:

```text
cursor = randring_p
sample = little_endian_word_starting_at(randring[cursor])
low_byte(randring_p)++
return sample / (sample & mask) / (sample % divisor)
```

Only the low cursor byte advances. With the high byte cleared by the fill,
ordinary samples at indexes 0 through 254 are:

```text
ring[p] | (ring[p + 1] << 8)
```

Consecutive samples therefore overlap by one byte. Index 255 is deliberately
different. The word load crosses the array boundary into the immediately
following low byte of `_randring_p`. Before that load the low cursor byte is
`0xFF`, so the boundary sample is:

```text
ring[255] | 0xFF00
```

The subsequent byte increment wraps the cursor to zero. It does not read
`ring[0]` as the high byte of this sample. The current linked MAP independently
shows `_randring` at `23FB:8BAE` and `_randring_p` at `23FB:8CAE`, exactly
`0x100` bytes later. The maintained state declaration and the already exact
accessor instruction bodies agree on this layout-dependent behavior.

The AND accessors consume and advance the sample before applying their mask.
They represent a uniform half-open range only when the requested width is a
nonzero power of two and the mask is `width - 1`. The MOD accessors likewise
advance first and then use unsigned 16-bit `DIV`, returning the remainder. They
have no zero-divisor guard; a zero width reaches the 8086 divide exception.
The range helpers also do not validate inverted or overflowing endpoints.

## Portable contract

The x64 implementation should own one explicit random-ring state object and
route both accessor families through it. It should preserve the descending
fill, overlapping little-endian samples, and call ordering. The index-255 value
should be synthesized as `ring[255] | 0xFF00`; relying on a C++ out-of-bounds
read or on native structure adjacency would introduce undefined behavior and
would not make the contract portable. A word cursor can be retained for state
clarity, but the increment operation remains explicitly byte-sized.

Changing the generator, splitting gameplay into multiple streams, wrapping
the high sample byte to `ring[0]`, or adding range guards are possible native
port policies only if recorded as intentional behavioral divergence.
