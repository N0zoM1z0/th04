# Build and matching bring-up

## Locally attested candidate

The private build environment now contains Turbo C++ 4.0J command-line tools
(`TCC.EXE` banner 4.02 and `TLINK.EXE` banner 6.10), TASM32 5.0, ReC98's
pinned MS-DOS Player P0281 binary, and Wine 8.0.  The complete acquisition,
installation, attestation, and operating instructions live in
`docs/TOOLCHAIN.md`; immutable identities live in `config/toolchain.toml`.

This is deliberately called a **locally attested candidate**, not a universally
canonical toolchain.  The TC4J media came from an HTTP-only third-party mirror
with no independently published digest.  We compensate with a pinned complete
media tree, installed trees, active binaries and configuration files, version
banners, embedded OMF producer comments, compiler dependency records,
deterministic execution probes, and reproducible cold output.  None of those
facts turns the download source into independent provenance.

ReC98 commonly uses the large memory model and flags equivalent to
`-O -b- -3 -Z -d`, with artifact-specific inputs and ordering.  That is useful
corroboration, not permission to assume every original TH04 translation unit
used one profile.  Probe individual ABI/code-generation claims.

ReC98 source remains an untrusted calibration fixture and is never copied into
`src/` wholesale.  Only outputs built locally from an attested environment can
become local evidence, and every required Oracle must still pass.

## TH01 cold-build calibration result

Two independently scripted local build materializations produced identical
TH01 final outputs.  Strict comparison against the legally supplied Japanese
TH01 target accepted only `ZUNSOFT.COM` byte-for-byte:

| Candidate | Raw verdict | Strict diagnostic |
| --- | --- | --- |
| `OP.EXE` | reject | Program image and relocation multiset match; ordered relocation table and header bytes differ. |
| `REIIDEN.EXE` | reject | Program image and relocation multiset match; ordered relocation table and header bytes differ. |
| `FUUIN.EXE` | reject | Program image and ordered relocations match; candidate header has 1,504 extra bytes. |
| `ZUNSOFT.COM` | exact | Complete 10,096-byte file matches. |

This is a useful upstream-policy differential.  ReC98's documented comparison
policy accepts the decompressed program image and an unordered relocation set,
while this project also gates the complete header, relocation order, padding,
overlay, and raw file.  The three rejections are expected evidence, not a
reason to weaken local policy.  `config/rec98_th01_calibration.toml` pins the
known vector so future comparator/toolchain changes must reproduce the same
result; it is not an exactness waiver.

## Required build receipt

Every exact comparison receipt must include:

- target artifact ID and SHA-256;
- source revision, tree, archive digest, and materialization method;
- compiler, assembler, linker, runtime, configuration, include, library, and
  runner identities;
- complete flags, macros, response-file contents, and environment whitelist;
- ordered source/object/library/link inputs and their SHA-256;
- OMF integrity, embedded producer, and dependency observations;
- output, map, object, and comparison-report SHA-256;
- whether the build was cold, isolated, deterministic, and serial;
- accepted extent and every relocation/layout rule;
- comparator version/commit and replay command.

Incremental builds may diagnose.  They may not publish aggregate exact totals.
